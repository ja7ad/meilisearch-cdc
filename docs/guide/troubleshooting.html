Troubleshooting and FAQ

Start with the task's status and its Logs tab: errors name the setting to change. This page collects the common ones.

Where to look

  1. The task's state. failed is a configuration problem (fix and start again); retrying is transient and resolves itself; held is a safety guard waiting for you.
  2. The task's Logs tab and the error under its status.
  3. The service log (journalctl -u meilisearch-cdc, docker logs cdc); set CDC_LOG_LEVEL=debug for more.
  4. Test connection in the task wizard, and the connector's last test.

"source position lost … starting a full resync"

Not an error to fix: the stored position no longer exists on the source (a purged binlog, an invalidated or dropped replication slot, an oplog that rolled over, an expired DynamoDB shard, a trimmed Redis stream, SQL Server change rows removed by cleanup, a position older than CockroachDB's GC window). The task copies everything again, with zero-downtime resync if enabled. If it happens often, keep tasks running or extend the source's log retention.

The task is held

A safety guard refused a risky batch; nothing was applied.

  • safety hold: a single batch would delete 5000 of 8000 documents (62% > 20% limit): check whether the source really deleted those rows. If yes, raise maxDeleteRatio (or set it to 0) and Resume, or Resync.
  • safety hold: the source table was truncated; enable safety.allowTruncate or resync the task: decide whether the index should be emptied too.

See safety guards.

Dashboard problems

  • "Offline" in the top bar behind a proxy: the proxy buffers Server-Sent Events. See Reverse proxy and TLS.
  • 403 cross-origin request refused on every save: the proxy changes the Host header; forward it unchanged.
  • Signed out after a restart: sessions survive restarts (they are stored); check that the data directory is persistent.
  • 429 too many attempts: wait 15 minutes or restart the service; behind a proxy enable CDC_TRUST_PROXY so one IP does not stand for everyone.
  • Forgot the admin password: meilisearch-cdc admin users reset-password --email … --generate. See recovery recipes.

The service does not start

  • The database is locked: another process (a second instance, or the CLI working offline) has cdc.db open. Run one instance per data directory.
  • cannot decrypt secret / value was encrypted with a key that is not configured: the key changed. Provide the old key as CDC_SECRET_KEY, or as CDC_SECRET_KEY_PREVIOUS to rotate. See key rotation.
  • task …: … then exit: the declarative tasks file has an error. See Declarative tasks file.
  • Permission denied on /data in Docker: a bind mount not writable by uid 65532. See Docker.

FAQ

Does it need Kafka or Debezium?
No. Most sources are read directly. Kafka is one optional source, for databases only Debezium supports.
Can one table feed several Meilisearch instances?
Yes: create one task per destination on the same connector and table. For PostgreSQL each task has its own slot.
Can several tables feed one index?
Yes, with the same primary key field and the upsert write mode, so each task merges its fields. Static fields help tell sources apart.
What delivery guarantee does it give?
At-least-once with idempotent writes: a change may be applied twice after a crash, never lost, and applying it twice gives the same document.
Can I run two replicas for high availability?
No. The state store is single-writer; run one instance and let your orchestrator restart it. Checkpoints make restarts cheap.
Does it change my database?
Only for PostgreSQL (a replication slot and, unless you name one, a publication per task) and CockroachDB (it may enable kv.rangefeed.enabled if allowed). Deleting a PostgreSQL task with drop source objects removes them.
How do I move an installation to another server?
Stop it, copy the data directory (with secret.key, or keep the same CDC_SECRET_KEY), start it there. See Backups.
